# BIBLE UNFOLDED — PERMANENT HEADQUARTERS RULEBOOK
## Binding Addendum: Mandatory Preflight, Deployment Verification and New-Chat Startup
**Owner directive: November 3, 2026.** This addendum supplements the existing BIBLE_UNFOLDED_PERMANENT_HEADQUARTERS_RULEBOOK and James's original addendum; it replaces or weakens nothing. Keep both originals intact. This GitHub copy is a persistent, easy-to-retrieve operational entry point, not a replacement for the complete archived rulebook.

### Mandatory first action in EVERY new conversation
Whenever the owner mentions Bible Unfolded, the Bible game, Story-Trails, Visual Lab, or requests any related project work, **before editing, committing, uploading, designing, or promising deployment**, fetch and read this rulebook entry point and the full permanent Headquarters rulebook available in ChatGPT Library / handoff files. Also read James's addendum and applicable mode-specific rules before modifying that mode. If the full rulebook is inaccessible, say so and obtain it rather than claiming it was reviewed. Check current repository state and previous approvals. This requirement applies even when the new chat begins with a short instruction such as "go", "next", or "fix this."

### Root-cause-first rule — explicit owner directive, November 3, 2026
**Never implement a fix before investigating and identifying why the original problem exists and why any previous fix failed.** Read the actual running implementation and relevant source, trace the loading/deployment path, reproduce or establish the failure with evidence, and only then choose the smallest appropriate correction. Verify that the correction addresses the identified cause; run tests and deployment checks before saying it works. If verification is unavailable, say precisely what remains unverified. Do not use the owner as the debugging or deployment-checking step; ask for input only when genuinely required. Waiting for publishing is acceptable; speculative fixes, false assurances, and repeated owner refreshes are not. **Read and apply this rule every time this rulebook is opened, including every new chat.**

### Non-negotiable QA and truthful status gates
1. **Inspect actual implementation first.** Read the relevant current HTML, CSS, JS, DOM structure, selectors, state, script loading, and dependent controls. Do not guess at class names, selectors, page structure, or asset paths from screenshots.
2. **Check code before committing.** Run syntax checks and appropriate structural/static tests; confirm selectors actually match the target; inspect CSS cascade and browser-specific behavior; validate asset URLs, case-sensitive filenames, and dimensions. Confirm no accidental hiding, overlay, click-blocking, navigation, or persistence regressions.
3. **Test functionality before requesting owner testing.** Verify relevant controls, gameplay transitions, menu/back behavior, responsive layout, scroll, saved state, and existing features. Compare baseline and candidate. If executable/browser testing isn't possible, state that clearly and do not claim it passed.
4. **Deploy only to Visual Lab first.** Do not touch Story-Trails LIVE without explicit owner approval for that specific promotion. Keep approved design/artwork and recovery baseline intact.
5. **Verify actual GitHub deployment.** After each commit, check GitHub Actions run result, latest branch SHA, installed loader in index.html, script and assets on published paths, and cache/version behavior. A successful commit alone is not a successful deployment. If a workflow fails, fix it before telling the owner to refresh.
6. **Verify rendered output where tools allow.** Use actual browser or screenshot inspection to confirm requested change visually appears and other controls remain. Test Chrome Android and Samsung Internet as feasible; James's physical iPhone/Safari acceptance remains separate. Do not claim physical-device verification from a simulated viewport.
7. **Report precise verification status.** Explicitly distinguish: code written, committed, workflow passed, published page verified, browser-rendered result verified, physical phone tested, and owner approved. Never say "done", "fixed", "live", or "ready to check" based solely on an unverified upload.
8. **Protect the owner's time.** Do not ask them to repeatedly refresh, wait 15 minutes, clear caches, or discover obvious bugs that could have been caught through the available tools. If the change is not verifiably deployed, explain the blocker immediately. Only ask for a final device check after all feasible assistant-side checks have passed.
9. **Handle failures honestly.** Stop, identify root cause, correct and rerun the gates, or revert. Do not stack untested patches. Do not silently change gameplay or remove buttons. Check per-browser saved-progress differences before attributing missing features to styling.
10. **Document evidence and handoff.** For each change note the files and commit SHA, tests run, results, limitations, rollback, and explicit owner approval. Include this rulebook/addendum in future handoffs and consult it at the start of every future Bible Unfolded chat.
